# نظام عمل — الواجهة الأمامية

واجهة React + Vite + Material UI باتجاه RTL لنظام إدارة وتوثيق مشتريات المبادرات.

## المتطلبات والتشغيل

- Node.js بإصدار حديث يدعم Vite 7.
- npm.

```bash
npm ci
npm run dev
```

لبناء نسخة الإنتاج:

```bash
npm run build
npm run preview
```

## إعداد API

تستخدم بيئة التطوير وكيل Vite لتمرير `/api` إلى الخادم، لتجنب CORS أثناء التطوير المحلي. اضبط:

```env
VITE_API_BASE_URL=/api
API_PROXY_TARGET=https://alzaman.mary4tech.com
```

- `.env.development` لتشغيل الوكيل المحلي.
- `.env.production` يحدد عنوان API المباشر للواجهة المنشورة.
- `.env.example` نموذج لإعداد التطوير المحلي.

تعاد قراءة متغيرات Vite عند تشغيل الخادم من جديد؛ أوقف `npm run dev` وشغله مرة أخرى بعد تغيير ملفات البيئة.

## المسارات التي تستخدمها الواجهة

- المصادقة: `POST /login`، `GET /user`، `POST /logout`.
- القوائم: `GET /categories`، `GET /locations`، `GET /units`، `GET /currencies`.
- المبادرات: `GET/POST /initiatives`، `GET/PATCH/DELETE /initiatives/{id}`، `PATCH /initiatives/{id}/status`، `GET /initiatives/trashed`، و`POST /initiatives/{id}/restore`.
- احتياجات المبادرة: `GET/POST /initiative-items`، `PATCH/DELETE /initiative-items/{id}`.
- الفواتير: `GET/POST /invoices`، `GET/PATCH/DELETE /invoices/{id}`، `GET /invoices/{id}/attachment`، `PATCH /invoices/{id}/status`، `GET /invoices/trashed`، و`POST /invoices/{id}/restore`.

تتوافق المسارات والحقول مع عقد API المتاح للفريق. يجب التعامل مع صلاحيات الخادم باعتبارها المرجع النهائي؛ إخفاء إجراءات الواجهة ليس بديلًا عن تحقق Laravel من الصلاحيات.

تتيح الواجهة للمدير إضافة الفاتورة من تفاصيل المبادرة وتعديلها أو حذفها مع مرفقها؛ ويمكنه استعادة الفواتير المحذوفة من تبويب «المحذوفات» في صفحة الإدارة. وتعرض الجداول حقول التدقيق عند إرجاعها من API (`created_by`, `updated_by`, `deleted_by`, `restored_by` والتواريخ المقابلة). يجب أن يحفظ الخادم هذه الحقول وأن يقيّد الحذف والاستعادة والتعديل بصلاحيات المدير؛ الواجهة لا تنشئ أعمدة قاعدة البيانات أو سجلات التدقيق.

## متطلبات الاتصال والتكامل

- يجب أن يعيد `POST /login` رمز المصادقة وبيانات المستخدم ضمن الاستجابة التي تعتمدها المجموعة، وأن يقبل الخادم رمز `Bearer` للطلبات المحمية.
- يحتاج نموذج المبادرة إلى تصنيفات ومواقع فعالة، ويحتاج حفظ الاحتياجات إلى وحدات قياس، ويحتاج إنشاء الفاتورة إلى عملات فعالة.
- يحفظ نموذج إنشاء المبادرة بياناتها فقط. تُضاف الاحتياجات لاحقًا من صفحة التفاصيل إلى `/initiative-items` مرتبطة بمعرّف المبادرة.
- بعد حفظ معلومات المبادرة وإضافة احتياج واحد على الأقل، يستطيع المالك إرسالها من صفحة التفاصيل عبر `PATCH /initiatives/{id}/status` بالحالة `wait_manager`. تظهر المبادرة للمدير للمراجعة، ويمكنه اعتمادها أو رفضها.
- تعرض أيقونة الشريط العلوي إشعارًا للمدير عند إرسال مبادرة للمراجعة، وللمنفذ عند موافقة المدير أو رفضه. يتم التحقق دوريًا كل 30 ثانية أثناء فتح التطبيق؛ لا يوفر عقد Backend الحالي خدمة إشعارات فورية.
- يتطلب رفض المدير إدخال سبب؛ تحفظ الواجهة السبب ضمن ملاحظات المبادرة ثم تغيّر الحالة إلى `manager_rejected`.
- يرسل نموذج الفاتورة الحقول `initiative_id`, `invoice_number`, `invoice_date`, `amount`, `currency_id`, `description`, `notes`, و`attachment`.
- يمنع API إنشاء أو تعديل المبادرة بتاريخ تنفيذ سابق؛ لذلك يمنع النموذج اختيار تاريخ سابق لليوم.
- لا يمكن تأكيد الاتصال بالخادم أو CORS أو صحة بيانات الدخول من داخل بيئة إعداد الملفات؛ يلزم اختبار ذلك من متصفح التشغيل ببيانات حساب API صالحة.

## قواعد مطبقة من دليل API

- تقبل الواجهة أدوار `requester` و`manager` و`accountant`؛ ويُعرض دور `requester` في الواجهة باسم منفذ المبادرة. جميع الأدوار المسجلة تستطيع إنشاء مبادرة، وفق الدليل.
- البحث والحالة والترقيم في قائمة المبادرات تُرسل كمعاملات إلى `/initiatives` بدل الاقتصار على السجلات المحملة في المتصفح.
- جدول المبادرات يعرض بيانات المنشئ والتواريخ ومعرّفات السجلات، ويوفر إجراءات العرض والتعديل والحذف والاحتياجات والفواتير وسجلات التدقيق للمدير. تصدير Excel متاح لنتائج البحث/التصفية كاملة بصيغة Excel XML (`.xls`) مع تهريب النصوص.
- يظهر عدد المستخدمين في صفحة الإدارة اعتمادًا على `meta.total` من استجابة `/users`، ويُعاد تحميل البيانات تلقائيًا بعد عمليات الإضافة والتعديل والحذف؛ لا يوجد زر تحديث يدوي.
- تعرض التكلفة الإجمالية من `total_cost` أو `total_amount` الذي يعيده API، أو تجمع الفواتير المضمنة مع المحافظة على فصل العملات. إذا لم يرسل API أياً من هذه البيانات فستظهر القيمة كغير متاحة، ويلزم عندها أن يعيد الخادم الإجمالي وعملته.
- عند استجابة `401` تمسح الواجهة رمز الدخول والمستخدم المحلي، وتعيد توجيه المسارات المحمية إلى تسجيل الدخول. أخطاء التحقق `422` تعرض أول رسالة حقل يعيدها الخادم ضمن `meta`.
- يتاح اعتماد/رفض الفاتورة للمدير فقط عندما تكون حالتها `pending`. يتحقق نموذج الرفع من الامتدادات `pdf`, `jpg`, `jpeg`, `png` ومن حد 2 ميجابايت.
- أُخفي إجراء تغيير حالة المبادرة عن المحاسب؛ يحذر الدليل من أن تحقق ملكية هذا المسار غير مكتمل على الخادم. يجب أن يبقى التحقق من الدور والملكية مطبقًا في API أيضًا.
- تتطلب القوائم `GET /units` و`GET /currencies` بيانات فعالة في الخادم؛ الاستجابة غير المتوافقة مع غلاف القوائم JSON تُعرض كخطأ بدل اعتبارها قائمة فارغة.
- `manager` هو دور الإدارة (`admin`) في الواجهة الحالية؛ لا يوجد دور API منفصل باسم `admin` في مجموعة Postman.

## حدود الأمان

- تضيف الصفحة سياسة CSP لتقييد مصادر السكربتات والاتصالات، وسياسة Referrer-Policy. يجب أيضًا إرسال `Content-Security-Policy` و`X-Content-Type-Options: nosniff` و`X-Frame-Options: DENY` و`Strict-Transport-Security` كرؤوس HTTP من خادم الاستضافة؛ ويفضل ضبط CSP كرأس HTTP بدل وسم HTML عند توفر إعدادات الخادم.
- تستخدم الواجهة حاليًا مصادقة Bearer وترسل الرمز في ترويسة `Authorization`، ولا ترسل Cookies افتراضيًا (`VITE_CSRF_ENABLED=false`)؛ لذلك لا تعتمد على حماية CSRF الخاصة بالكوكيز حتى يدعمها Backend.
- يمكن تجهيز تكامل CSRF بعد دعم الخادم عبر ضبط `VITE_CSRF_ENABLED=true` و`VITE_CSRF_COOKIE_URL` إلى رابط إصدار رمز CSRF الكامل. عند التفعيل، تطلب الواجهة رمز الحماية قبل طلبات POST/PUT/PATCH/DELETE، وترسل كوكيز الاعتماد وترويسة `X-XSRF-TOKEN` المأخوذة من `XSRF-TOKEN`. لا تفعّل ذلك قبل أن يجهز Backend نقطة إصدار الرمز والتحقق منه، وكوكيز آمنة، وCORS بقائمة origins محددة و`Access-Control-Allow-Credentials: true` والسماح بترويسة `X-XSRF-TOKEN`. أعد بناء الواجهة بعد تعديل متغيرات البيئة.
- لا يمكن فرض CORS من React؛ وكيل التطوير لا يضبط CORS في الإنتاج ولا يحمي API. يجب أن يسمح Backend بأصل الواجهة المنشور المحدد فقط، مع ترويسة `Authorization` والطرق المطلوبة، ومن دون `Access-Control-Allow-Origin: *` عند استخدام بيانات اعتماد.
- لا تتوفر ملفات Backend أو إعدادات الاستضافة هنا؛ يجب تطبيق إعدادات CORS وCSRF ورؤوس الأمان المذكورة على الخادم/الوكيل العكسي. يظل تخزين رمز Bearer في `localStorage` معرضًا للقراءة عند حدوث XSS؛ الحل الأقوى يتطلب دعم Backend لجلسة `HttpOnly`, `Secure`, `SameSite` مع CSRF token.
- تُعرض جميع قيم API ومدخلات المستخدم عبر React كنصوص، ولا تستخدم الشيفرة `dangerouslySetInnerHTML` أو واجهات إدراج HTML خام. تعرض SweetAlert الرسائل باستخدام `text` لا `html`، ويُهرب تصدير Excel قيم الخلايا قبل تضمينها في XML. لا تُضف عرض HTML غني من بيانات المستخدم أو الخادم دون منظّف HTML موثوق وسياسة سماح محددة.
- تطبق الصفحة CSP تمنع السكربتات المضمنة ومصادر السكربت الخارجية، وتحظر الكائنات والإطارات والنماذج المرسلة إلى مصادر خارجية. تتحقق الواجهة من المدخلات لتحسين الاستخدام، لكن التحقق النهائي يجب أن يظل في Backend.
- لا يمكن تفعيل CORS من React؛ يجب ضبط قائمة origins المسموح بها ورؤوس CORS على الخادم/الوكيل العكسي. مجموعة Postman تستخدم Bearer token، ولا توثق مسار CSRF أو جلسة Cookie.
- إذا استمر استخدام Bearer token المخزن في `localStorage`، فإن أي XSS ناجح قد يقرأه. التوصية للخادم هي جلسة `HttpOnly`, `Secure`, `SameSite` مع CSRF token عند اعتماد مصادقة Cookie، وسياسة CSP ورؤوس أمان كـHTTP response headers. لا تتوفر ملفات Backend هنا لتطبيق هذه الإعدادات أو فحصها.

## إدارة البيانات المرجعية

- أُضيفت صفحة `/admin` للمدير فقط، وتتيح عرض/إضافة/تعديل/حذف العملات والتصنيفات والمواقع ووحدات القياس، مع شاشة موحدة لعرض السجلات المحذوفة واستعادتها.
- في شاشة العملات، حقل `name` وحقل `code` إلزاميان، ويُرسل `code` إلى الخادم كما هو بعد تحويله إلى أحرف كبيرة. يظل التحقق من تفرد الرمز مسؤولية الخادم.
- تتضمن صفحة الإدارة إنشاء المستخدمين وتعديل بياناتهم وأدوارهم وتفعيلهم/تعطيلهم وقفلهم/فك قفلهم، إضافةً إلى عرض سجلات التدقيق وحذفها وعرض المحذوف منها واستعادته.
- تعرض صفحة المحذوفات الموحدة موارد العملات والتصنيفات والمواقع والوحدات والمبادرات والفواتير وعناصر المبادرات وسجلات التدقيق. قد يرفض الخادم الاستعادة إذا كانت غير مسموحة وفق حالة المورد أو ملكيته؛ تعرض الواجهة رسالة الخطأ بدل تجاوز القيد.

## حدود التحقق والتسليم

- نجح `npm run build` بعد التغييرات، وأظهر `npm audit` عدم وجود ثغرات في الاعتماديات الحالية. لم يُختبر الاتصال بواجهة API حقيقية.
- لا يمكن تأكيد توفر البيانات الفعلية في قاعدة البيانات أو صحة CORS وبيانات الدخول دون تشغيل الواجهة أمام API حقيقي.
- صفحة التقارير لا تعتمد على مسارات تقارير غير موجودة في مجموعة Postman؛ فهي تعرض ملخصًا مشتقًا من البيانات التي تستطيع الواجهة قراءتها.
- إدارة الحساب الشخصي للمستخدم النهائي عبر `/users/{id}`، وعرض تفاصيل سجل التدقيق الفردي، ليستا شاشتين منفصلتين في هذه النسخة؛ بقية إجراءات المستخدمين وسجلات التدقيق المتاحة في المجموعة موجودة في صفحة الإدارة.
- يجب على مهندس الخادم تأكيد صلاحيات المسارات ومراجعة خلل ملكية `PATCH /initiatives/{id}/status` المذكور في دليل التكامل قبل النشر؛ إخفاء الأزرار في الواجهة ليس بديلًا عن حماية الخادم.
- لم يتم استخدام بيانات الدخول المذكورة للوصول للموقع الخارجي. وبما أنها أُرسلت ضمن المحادثة، يُستحسن تغيير كلمة المرور قبل استخدامها مجددًا.
